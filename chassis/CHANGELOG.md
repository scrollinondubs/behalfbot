# Chassis Changelog

Single source of truth for chassis releases. Read by the auto-updater (issue #33) to surface diffs and detect breaking changes.

## Format conventions

Each release is a `## vX.Y.Z` heading. Under it:

- **Added** / **Changed** / **Fixed** / **Removed** subsections (any subset)
- **BREAKING CHANGES:** marker (uppercase, on its own line) when a release requires manual review before applying. The auto-updater notification flips into `--force` mode whenever this marker appears for an unreleased version between the customer's `current` and `latest`.
- **Migration:** subsection pointing at `scripts/chassis-migrations/vX.Y.Z.sh` if the bump needs a state migration. Migration scripts are strictly automated shell scripts only (no Claude judgment, no LLM calls). Judgment-heavy migrations get flagged as BREAKING CHANGES and gated behind explicit operator review.

Semver:

- `MAJOR` (`1.0.0` → `2.0.0`): always BREAKING. Reserved for chassis architecture changes (Docker image base, dispatcher API, subtree layout).
- `MINOR` (`0.3.0` → `0.4.0`): new features, optional fields, opt-in behaviors. Backwards-compatible.
- `PATCH` (`0.3.1` → `0.3.2`): fixes, prompt tweaks, internal refactors. Always backwards-compatible.

## Unreleased

### Added

- **An install can now be stopped from Discord with no shell, no ssh and no working Claude session (new-jaxity#550).** Between 2026-09-01 and 2026-09-05 the reference install's operator was off-grid. A heartbeat fired every 30 minutes on a condition only he could clear: 514 model invocations, $45.79, 66% of all scheduled spend for the period, 50+ near-identical messages into one channel, over four days. In the same window his Tailscale node key hit its 180-day expiry (no ssh, no VNC) and the macOS Keychain lost the Claude Code OAuth token (the host `claude` session that serves Discord was dead, so replies reached nobody). He watched it arrive on his phone for four days, then drove home and pulled the power cord out of the Mac Mini.
  - Conservation mode already existed and would have stopped most of that spend. It is flipped by `scripts/conservation-mode.sh`, which needs a shell, which is the one thing he did not have. **Every stop path the chassis had shared a dependency with something that was down.** That is the defect, not the runaway heartbeat.
  - New `chassis/scripts/discord-control-listener.py`: a standalone process that polls the Discord REST API with the bot token, matches a fixed lexicon from the install's principal, writes the dispatcher's flag files directly, and acks in-channel. No model in the path, no shell in the path. `halt` / `mute` / `silence` stops everything; `resume` / `unmute` clears both flags; `conserve` / `throttle` throttles; `unconserve`; `status`. An optional `30m` / `2h` / `3d` becomes `auto_lift_after`, and the remainder becomes the reason.
  - **New `scheduled-tasks/halt.json`, checked before conservation mode and ignoring `criticality` entirely.** Conservation lets `critical` heartbeats through, which is right for a quota throttle and wrong for an operator asking for silence. Halt ends the tick. Same five-key schema as `conservation-mode.json` rather than a parallel one, so `backup-to-s3.sh`, `gather-quota-check.sh` and `scripts/conservation-mode.sh` need no new vocabulary.
  - **Omitting the duration means no auto-lift, deliberately.** An auto-resume that fires while the operator is still off-grid restarts the outage, and by definition they are not there to see it.
  - **The ack says what halt does NOT stop**, because in the moment it is the only documentation the operator has: an in-flight `claude -p` finishes (up to ~40 min with retries), host-side launchd/systemd jobs are not covered, a live interactive Claude session is not covered, and the listener itself keeps running because it has to hear `resume`. A kill switch that overstates its reach is worse than none.
  - **Authorisation reuses `CHASSIS_PRINCIPAL_USER_ID`** (the principal-policy hook's id), falling back to `INSTALLER_DISCORD_USER_ID` (the id `bootstrap-discord-access.sh` already requires). That hook fails OPEN on a missing id, correctly: a misconfigured install should not lose its prompts. **This one fails CLOSED** - it refuses to start, exits 78, and the entrypoint writes `remote kill switch UNARMED` plus the reason into the container log. A kill switch that silently never arms is the exact failure shape being fixed. `bootstrap-audit.sh` gains Gap 6 for the same condition, and it fails on the reference install today, which is the point.
  - **The cursor only ever reads forward.** Cold start synthesises a snowflake from the current time; a persisted cursor is honoured but capped at `CHASSIS_CONTROL_LOOKBACK_SECONDS` (default 1h). A listener that replayed history on restart would re-execute a four-day-old `halt`, or worse a `resume` sent before the thing it was meant to stop existed.
  - **State is written before the ack**, so a halt takes effect even when the POST fails. The ack is the operator's confirmation, not the mechanism. Every HTTP failure returns `None` and the loop continues: there is no error worth dying for in a process whose only job is to still be alive when someone types `resume`.
  - **Matching is on the whole message.** "we should probably halt the drift alert" does nothing. There is no model here to read intent, and a substring match would mean the operator cannot discuss the kill switch in the channel it listens on. `stop` is deliberately not in the lexicon - people type it mid-conversation to interrupt.
  - **It runs as a supervised child of the dispatcher loop, not a new compose service.** Existing installs gain the switch by pulling an image, with no customer-side compose edit - which matters more here than the isolation a separate container would buy. A `control-listener` entrypoint mode exists for installs that want to run it separately anyway. The child is deliberately not waited on: a wedged dispatcher tick must not take the switch down with it.
  - Polling rather than a gateway websocket: 20-second polls on one channel are a handful of requests a minute against a 50/s bucket, and reuse the same REST surface `discord-post.sh` has used since 2026-05-27. A gateway connection means a library, an intent configuration and a reconnect state machine in the one process that must not fail to start.
  - Coverage: `chassis/scripts/tests/test_discord_control_listener.py`, 49 cases, stdlib only (no `requests`, so the CI job needs no new dependency). It proves the things that make it a kill switch rather than a parser: a non-principal `halt` writes nothing and acks nothing, a stale cursor is capped, a batch is applied oldest-first (Discord returns newest-first, so a `halt` then `resume` in one batch would otherwise land reversed), the flag reaches disk when Discord is unreachable, a failed write still tells the operator, and the REST client returns `None` on 403 / DNS failure instead of raising.
  - `docs/remote-kill-switch.md` documents the lexicon, the coverage boundary, the configuration and the design calls.

- **CI now runs the shell suites on macOS bash 3.2 with a BSD userland, not only on ubuntu (new-jaxity#550).** Chassis code runs in two places - the Debian container (bash 5.x, GNU coreutils) and the operator's macOS host, where `/bin/bash` is 3.2.57 and the userland is BSD - and CI only ever exercised one of them. Three bugs shipped green through the ubuntu-only lane on 2026-09-05 and broke on contact with a real machine: `${BAKED_ROOTS[-1]:-}` in `resolve-plugin-root.sh` (negative subscripts need bash 4.3; on 3.2 it errors and expands to EMPTY, so the resolver handed callers an empty plugin root on the compose-failure path, #197), `stat -f %m` in the colima work (a filesystem query on GNU, an mtime query on BSD; chained with `||` the outputs concatenated and disabled a recycled-pid lock breaker, #193), and `date -j -f` in `is_conservation_mode()` (#195, below).
  - **The third one broke on Linux because the code was BSD-only.** So this is not "add macOS support", it is "both target platforms must be exercised", and every new check is symmetric.
  - New `macos-bash32` job in `.github/workflows/shell-tests.yml` runs the same thirteen suites the ubuntu jobs run - deliberate parity, since a divergence between the two lists is how one lane quietly stops covering something. It runs in parallel with them and adds no serial time to a PR.
  - **The job pins bash before it does anything else, and fails if the pin did not take.** The suites invoke their subjects as `bash "$SCRIPT"` and half of those carry `#!/usr/bin/env bash`, so both resolve through PATH. GitHub's macOS image ships Homebrew, which can put bash 5.x ahead of `/bin`, and the lane would then be a second ubuntu lane wearing a macOS hat. A shim dir pins `bash` to `/bin/bash`, and a separate step asserts `bash`, `env bash` and `/bin/bash` all report 3.2.x, that a negative array subscript is genuinely broken here, and that `stat`/`date` take BSD flags and reject GNU ones.
  - **It counts assertions, not exit codes.** Each suite must report a non-zero assertion count and the run must total at least 340 (it totals 365 today). A suite that exits 0 having asserted nothing is the exact failure class this whole lane exists to catch.
  - Proven to discriminate: with `${BAKED_ROOTS[-1]:-}` put back, `test-plugin-root-resolution.sh` reports 44 passed / 0 failed under bash 5.2 on Debian and 43 passed / 1 failed under bash 3.2.57 on macOS, failing on `s8 falls back to baked` with an empty root.
  - New advisory `portability` job in `.github/workflows/shell-lint.yml`, backed by `.github/scripts/check-shell-portability.sh`. shellcheck runs at `severity: error` and does not know which bash version or which userland this code must survive, so it had nothing to say about any of the three bugs. The check greps for bash-4-only constructs (negative subscripts, associative arrays, `mapfile`, `${var^^}`, namerefs, `coproc`, `&>>`, `;;&`) and for BSD/GNU splits (`date -j` vs `date -d`, `stat -f` vs `stat -c`, `sed -i`, unguarded GNU coreutils). Dialect pairs are matched over a 7-line window so the ordinary two-line fallback idiom does not warn, and for `stat` the window checks ORDER, because GNU `stat -f` writes a filesystem block to stdout before failing.
  - It is advisory (`continue-on-error`) because it is a heuristic and blocking a PR on a heuristic is how a check gets deleted. Its self-test is not: `.github/scripts/test-check-shell-portability.sh` runs 30 assertions proving the three bugs verbatim still fire and that the fixed spellings already in the tree produce zero findings. Escape hatch is a trailing `# portable-ok: <which platform, and why>`.
  - It reports 12 findings on the tree as it stands, every one of them a pre-existing single-platform line, filed separately rather than fixed here.

### Fixed

- **Conservation mode's auto-lift has never worked inside the container, and the log line for the broken path is the same one the working path prints.** `is_conservation_mode()` parsed `auto_lift_after` with `date -j -f ... || echo 0`. `date -j` is BSD only, so on Debian (every containerized install) the parse always failed, `lift_epoch` became 0, `now >= 0` was always true, and **any `conservation-mode.json` carrying a non-null `auto_lift_after` was disabled on the very next tick** - the throttle with an expiry was the one that could not survive fifteen minutes. It logged `CONSERVATION - auto-lift triggered`, which is exactly what a correct auto-lift logs, so nothing could surface it. Found while building the halt flag, which needed the same arithmetic and would have inherited the same bug.
  - The parse moves to new `chassis/scripts/_control-flags.sh`, shared by both flags so they cannot drift apart on what "expired" means. It tries BSD, then GNU, then `python3`.
  - **An unparseable timestamp now keeps the flag ON rather than lifting it.** For a kill switch the direction of the failure matters more than the failure: a halt that quietly lifts itself because a date string was malformed is the outage this whole feature exists to end. Same for a flag file that exists and cannot be read.
  - Every command substitution in the library is guarded with `|| x=""` and every local is `_cf_`-prefixed. The file is sourced into a `set -euo pipefail` zsh dispatcher, where one bare `x=$(false)` takes the tick down - a library that turns a kill switch into an outage would be a poor trade.
  - The dispatcher keeps a degraded inline fallback for the case where the library is missing, so a partial update loses the auto-lift arithmetic and not the switch.
  - Coverage: `chassis/scripts/test-control-flags.sh`, 30 assertions, wired into `shell-tests.yml`. It stubs `date` on PATH to force each dialect and runs the full matrix three times, and it asserts directly that the PRE-fix idiom still misparses a future expiry under GNU date - if that assertion ever starts failing, the suite has stopped proving anything about the bug it was written for. It also proves the library survives being sourced under `set -euo pipefail` in both bash and zsh.

### Fixed

- **A hard power-off left every container on the reference Mac dead, and two launchd jobs both failed to bring it back (new-jaxity#550).** An unclean shutdown leaves Lima's `ha.pid` / `vz.pid` / `ha.sock` / `ssh.sock` behind in `~/.colima/_lima/<instance>/`. After the reboot those pid files point at PIDs the kernel has reissued to unrelated processes - on 2026-09-05 the stale pid was 789, by then `sirittsd` - so Colima believes the VM is alive and every command talks to a socket nobody is listening on. `colima list` reads `Broken`, `colima status` says not running, `docker ps` cannot reach the socket, and `colima start` dies with `errors inspecting instance: [failed to get Info from ".../ha.sock": dial unix .../ha.sock: connect: connection refused]` while `daemon.log` loops `waiting 5 secs for VM` forever. Postgres, the note-taking app and the chassis container running the heartbeat dispatcher all stayed down.
  - **The retry that was there could not work, because `colima start` reads the same stale files on every attempt.** The old `com.behalfbot.colima` plist ran `colima start -f` directly and a hand-written postgres agent ran `colima status || colima start ...`; both fired at boot, both failed, and neither had a way out. New `chassis/scripts/colima-ensure.sh` runs the one command that does clear it, `colima stop --force`, then retries `colima start` exactly once. `stop --force` removes the stale pid and socket files and flips the profile back to `Stopped`; it is non-destructive and does not touch the VM disk image.
  - **The wrapper is structurally incapable of running `colima delete` or `colima start --reset`, and the suite asserts that on every path.** Both are the commonly suggested fix for a wedged Colima and both destroy the VM disk image, taking every docker volume with it - on the reference install a 20GB image holding Postgres and the note app's workspace with no other copy on the box. A recovery script that can reach for them is worse than no recovery script. Two assertions cover it: no scenario ever issues either command, and no line invoking `$COLIMA_BIN` mentions them, so a later edit adding one fails CI rather than review.
  - **`docker ps` is the success signal, not the `colima start` exit code.** A start that exits 0 onto a socket still refusing connections is exactly the state being fixed, so a wrapper that trusted the exit code would report success on the failure it exists to catch. It also skips the first `colima start` outright when the profile already reads `Broken`, because against a Broken profile that attempt fails every time and costs a minute of boot.
  - **`com.behalfbot.colima` is now shipped from chassis as a template and is the single owner of Colima startup.** It is the one chassis-shipped plist that legitimately belongs in the daemon domain per `docs/launchd-domains.md`: no login keychain, no `claude`, no shared tmux server, and it has to come up on an unattended reboot with nobody logged in. Registered only where Colima is actually the Docker runtime, so a Linux install and a Mac without Colima are never made to sudo for a plist that would no-op. The label is deliberately not bot-scoped - Colima is a per-machine singleton, so two installs on one Mac must share one owner.
  - **The old plist's `KeepAlive { SuccessfulExit: true }` respawned the job when it exited zero and left it alone when it failed**, so the one case that needed a retry was the one case launchd never retried; it sat parked at exit status 1 while Docker stayed down, and its own comment claimed the opposite. Replaced with `RunAtLoad` plus a 300s `StartInterval`, which the idempotent wrapper turns into both boot recovery and continuous self-heal without the hot-loop risk of KeepAlive-on-failure against a VM that genuinely cannot start.
  - **The wrapper holds a lock, and staleness is decided by age as well as pid liveness.** Recovering the reference install by hand meant booting out `postgres-watchdog`, `container-liveness` and `terminal-watchdog` first so they would not race the repair. `kill -0` on a recycled pid succeeds for a completely unrelated process, which is the same defect the whole fix is about, so a pid check alone would deadlock the box permanently on exactly the condition it is meant to survive.
  - **The duplicate owner chassis cannot fix is now detected and named.** Both second owners on the reference install were customer-written plists, and silently rewriting someone's own launchd job is not something the bootstrap should do. `bootstrap-customer-scripts.sh` scans both launchd domains on every plist render, follows one level of indirection into the shell scripts those plists invoke, and warns with the exact remediation. Verified against the reference host: it finds both real second owners, one declaring `colima start` inline in the plist and one reaching it through the shell script the plist schedules, and false-positives on none of the two dozen other plists on the box. `docs/colima-recovery.md` carries the worked example. The same change fixes the stale-daemon check, which flagged every plist in `CHASSIS_PLIST_DOMAINS` found in `/Library/LaunchDaemons/` and would therefore have refused to proceed on every correctly configured macOS install the moment a daemon-domain plist was added.
  - **Tailscale node keys expire after 180 days, silently, and take ssh and VNC with them.** That is the other half of #550: the key was issued the day the box was provisioned, hit its 180 days while the owner was away, and removed every remote path to the machine on the same morning the Claude Keychain entry emptied. `docs/installer-homework.md` gains it as a pre-install checklist item with the per-node disable steps, because the tailnet-wide setting under Device management caps at 180 days and cannot disable expiry at all. The verify command is `tailscale status --json | jq '.Self.KeyExpiry'`, run against this host rather than copied from memory - the first draft used a `grep -A2 '"Self"'` pipeline that matches nothing.
  - Coverage: `test-colima-ensure.sh`, 31 assertions, wired into `shell-tests.yml`. Stubs both `colima` and `docker` and overrides the OS probe, so it needs no VM, no daemon and no Mac. Proven to discriminate rather than merely to pass: 14 of its assertions fail against a naive `colima start` implementation. It also earned its keep immediately by failing on the Linux runner while passing on macOS: `stat -f %m` is a filesystem query on GNU coreutils, not an mtime read, and it prints a whole filesystem block to stdout before exiting non-zero, so chaining it with the GNU spelling inside one command substitution concatenated both outputs and every stale lock parsed as age 0. The branch that silently could not run on Linux was the recycled-pid lock breaker, which is the same class of defect the whole entry is about. A second CI-only failure came from the suite itself: the scenarios that assert what happens when colima or docker is absent set `PATH=/usr/bin:/bin`, and a GitHub Actions runner ships a real `/usr/bin/docker` with a live daemon behind it, so "docker is missing" quietly became "docker answers" and the branch under test was never reached. Those scenarios now run against a PATH holding symlinks to exactly the four externals the script needs and nothing else. Both failures are the reason the suite runs on a Linux runner rather than only where it was written. New `docs/colima-recovery.md` carries the full error signature for whoever greps their way there next, plus the migration for existing installs.

- **A wrong parameter name on the Discord reply tool silenced an install for four hours (#511 customer-side).** The reply tool's body parameter is `text`. A call passing `message` arrives with `text` undefined and dies inside the plugin's own `chunk()` splitter with `reply failed: undefined is not an object (evaluating 'text.length')`. The error names a plugin internal rather than the parameter, so the failure reads as a plugin fault: the reference install spent an hour reading plugin source on 2026-08-13 while its installer received nothing, and the terminal transcript looked healthy throughout. Anthropic's Discord plugin is the real root - it could accept `message` as an alias, or raise an error that names the field - but every install running that plugin can hit this today.
  - New `chassis/.claude/hooks/discord-reply-param-fix.sh` renames the key in flight via `hookSpecificOutput.updatedInput`. It is a PreToolUse hook that **denies nothing**, which is new for this layer; `docs/security.md` gains a section distinguishing correctness rewrites from the safety blocks so the two are not confused.
  - **Silence on the common path is the safety property, not a nicety.** This hook fires ahead of every Discord reply, so a hook that emits an `updatedInput` when none is needed is a hook rewriting payloads it does not understand. Correct calls produce no output at all.
  - **Every `jq` in it fails open.** A non-zero exit from a PreToolUse hook can block the call, and a hook that mutes the Discord channel on malformed stdin defeats its own purpose. The first draft did not: `set -euo pipefail` propagated `jq`'s exit 5 on unparseable input, and the test suite caught it before the hook shipped.
  - **`docs/security.md` now documents how hooks are registered at all.** They ship in this repo but are wired host-side in `~/.claude/settings.json`, and that step was written down nowhere - a hook present on disk and absent from that file does nothing, with nothing to surface the gap.
  - Coverage: `test-discord-reply-param-fix.sh`, 24 assertions, wired into `shell-tests.yml`. Proves the rewrite carries `chat_id` / `reply_to` / `files` across (a rewrite that drops the attachment list turns a loud failure into a quiet one), that a multiline body with quotes and backslashes survives the round trip byte for byte, that all six non-bug paths stay silent, and that malformed and empty stdin exit 0.

- **The update path was blind to every merge that landed under an unchanged `VERSION` (#147).** `chassis/VERSION` moves only on an explicit release commit, but `main` is the distribution branch: `chassis-update.sh` hardcodes `UPSTREAM_BRANCH="main"`, and the latest release tag was `v0.1.1` while `VERSION` read `0.5.0`. Both `gather-chassis-update-check.sh` and `chassis-update.sh` gated on string equality between local and upstream `VERSION`, so the moment those matched, the checker emitted `{"count": 0, "reason": "up_to_date"}` forever and the applier answered `update chassis` with "Already up to date. Exiting." On 2026-08-09 the reference install sat nine commits behind an upstream reporting the same version number, including #142's fix for a `bootstrap-audit.sh` check that could never pass, while a bug had been silently destroying its knowledge graph for sixteen days. Cutting v0.5.0 unblocked that install; this stops it recurring, there and on every install that tracks `main`.
  - The signal is a digest of the `## Unreleased` section, compared **local tree against upstream** rather than upstream against a stored baseline. Local-versus-upstream measures the condition that matters ("this tree differs from what an apply delivers") instead of a proxy ("upstream moved since we last said something"), needs no seeding - a stored baseline has a cold start where the first run after shipping either fires on every install or silently records an already-drifted install as level, which is the failure being fixed - and self-clears after an apply with no state write. New shared `_chassis-changelog.sh`, sourced by both the checker and the applier so they cannot disagree on what drift is.
  - **The gap is named rather than hidden: a merge that lands code and adds no changelog entry moves no digest and stays invisible.** The durable complement is requiring a changelog entry per PR, which is CI work and a separate issue. Keying on the upstream commit SHA for `chassis/` via the GitHub API was considered and rejected: exact, but it puts an authenticated-or-rate-limited dependency into scripts that today need neither.
  - **The emitted JSON now carries an explicit `kind`**, `version` or `drift`, because a drift offer has `current == latest` and both consumers - `chassis-update-check-prompt.md` and the `chassis-update` skill - were written assuming otherwise. Both handle the drift shape; a notification the apply path cannot act on would be worse than no notification.
  - **The applier had three separate blockers, not one.** Beyond the version-equality gate, the post-pull check died with "pull did not advance the chassis tree" - true of every drift apply by definition - and the healthcheck compared `VERSION`, which for drift passes on the first poll whether or not anything happened, the exact tautology `_chassis-update-health.sh` exists to warn about. All three now take the digest as evidence, including a `docker exec` read of the container's own `CHANGELOG.md` digested host-side. Migrations are skipped on a drift apply: `vX.Y.Z.sh` already ran when that version was applied.
  - **`dismissed.json` is now keyed per offer.** `skip update` on a drift offer writes `<version>+<digest>`, so the next merge under the same version is still surfaced; a bare version string keeps its old meaning of muting that version entirely, which is what every entry written before this change means and what `skip update` on a version offer still writes.
  - **The `BREAKING CHANGES:` window now includes `## Unreleased`**, for version offers too. A pull of `main` delivers the unreleased commits along with the released ones, so a marker sitting under `## Unreleased` was being applied while the notification said no review was needed. Capture deliberately starts at the `## Unreleased` heading rather than the top of the file, because the format-conventions preamble above it contains the literal marker text.
  - **Cost contract changed on purpose.** The changelog GET moves above the up-to-date gate, so the common path is two unauthenticated `raw.githubusercontent.com` requests on a weekly heartbeat instead of one. The alternative was keeping a checker that structurally cannot see what it exists to see.
  - Coverage: `test-chassis-update-check.sh` grows from 23 to 46 cases and `test-chassis-update-mode.sh` from 42 to 54, the latter including real `git pull` runs against a local bare repo because two of the three applier blockers are unreachable from `--dry-run`. Run against `origin/main`'s scripts, 20 and 12 of those cases fail respectively, so the suites are proven to catch the defect rather than merely to pass.
- **The memory canary's own wrapper could not find it (#151).** `gather-memory-canary.sh` derived the canary's path from `CHASSIS_HOME` (`${CHASSIS_HOME}/chassis/scripts/memory-canary.sh`). That names the chassis tree only on a host-side install. Inside the container `CHASSIS_HOME` is the CUSTOMER root, so the path resolved to `/app/customer/chassis/scripts/`, which exists on neither container shape - not the baked layout (`/app/chassis`) and not the mounted-clone layout (`/app/customer/chassis/chassis`). On the reference install the canary passed by hand while the gather wrapping it reported `count=1, stage=unavailable`: the monitor calling itself dead. Wired at `criticality: critical`, that pages daily about a monitor that is working.
  - The gather now resolves the canary from its own `SCRIPT_DIR` first (they ship in the same directory, so a sibling cannot be the wrong tree), falls back to `chassis-root.state.json` read the way `gather-chassis-root-health.sh` reads it, and only then to the legacy host layout. The unavailable message now names every location searched instead of one.
  - `gather-bootstrap-audit.sh` carried the same idiom and the same consequence, quieter: it emits `count=0, "cannot gate"` when the audit is missing, so the bootstrap audit has silently never run on a containerized install. Same resolver, same order; its quiet-on-missing contract is unchanged, because that gather is not `criticality: critical`.
  - **The registration in `HEARTBEATS.md.template` was wrong in a second, independent way.** Its `gather:`/`prompt:` convention is `${CHASSIS_HOME}/chassis/...` for chassis-shipped files. Gather lines are `eval`ed, so that expands - to a path no container has. Prompt paths are never variable-expanded; the dispatcher joins the raw string onto `$CHASSIS_HOME`, so the templated prompt becomes the literal `/app/customer/${CHASSIS_HOME}/chassis/...` and the heartbeat would have died with `prompt_missing` the first time it fired. Both legs of the memory-canary block now address the boot-time `state/chassis-root` symlink relative to `$CUSTOMER_HOME`, which resolves on both container layouts. The path-conventions section documents the container case and the host-install caveat; the other heartbeat blocks still carry the old idiom and are left for a follow-up.
  - Coverage: `test-memory-canary.sh` gains a chassis root that is not `$CHASSIS_HOME/chassis`, resolved via the state record, plus a stale state record that must still fire rather than pass; `test-bootstrap-audit-memory.sh` gains sibling and offset-root resolution cases for the audit gather. Three of the five discriminate: the two offset-root cases and the audit sibling case fail against the pre-fix scripts. The stale-record and quiet-on-missing cases pass either way by design - they pin behavior the fix had to preserve rather than behavior it introduces.

## v0.5.0 - 2026-08-09

Sixteen commits that had accumulated on `main` under an unchanged `VERSION`. That is not incidental to this release: because both `gather-chassis-update-check.sh` and `chassis-update.sh` gate on string equality between local and upstream `VERSION`, every one of these commits was structurally invisible to every install's update path until this bump. The reference install was nine commits behind an upstream that reported the same version number, including the fix for a bug that had been silently destroying its knowledge graph. See #147.

### Added

- **A silently amnesiac install now pages within a day (#145).** #142/#143 fixed the detector that could never pass; this adds the detector for the failure that actually happened. Sean's memory MCP knowledge graph was unreachable from inside the chassis container for at least sixteen days (2026-07-24 to 2026-08-09) because `.mcp.json` baked an absolute host path that does not exist in the container namespace. Nothing caught it: writes did not error in a way anything collected, and a read from a broken graph returns a well-formed empty result, which is indistinguishable from "no prior context". Gap 3, even after #143, asserts the graph is *writable* - a writable, reachable, completely unused graph passes it clean, which is exactly the state that install was in.
  - `memory-canary.sh` does a write-read-verify round trip: it writes a per-run nonce to the reserved entity `health:memory-canary` using the exact command `.mcp.json` declares, then reads it back **in a separate server invocation** and asserts the two match. The separate read-back is the load-bearing part - a same-process round trip would pass against an in-memory cache while the file path was broken, which is the #142 bug wearing the opposite sign. Separation is structural: three independent process spawns (clear, write, read) sharing nothing but the graph file. Failures name the resolved path, the config shape and the exact error, so the first line of the alert identifies the namespace problem rather than saying "memory broken".
  - Deliberately NOT an mtime staleness threshold. Memory writes are event-driven, so a quiet week is indistinguishable from a broken graph; any threshold either false-alarms or is loose enough that it would not have caught the sixteen-day outage until late. It would also measure a proxy (are writes happening) instead of the property that matters (can this install write and read back its own memory).
  - `gather-memory-canary.sh` + `memory-canary-prompt.md`, registered in `HEARTBEATS.md.template` as a default-on `daily 07:00` heartbeat with `criticality: critical`. The gather ALWAYS exits 0 and carries the verdict in `count`, because the dispatcher treats a non-zero gather exit as count=0 - a gather that exited non-zero on failure would go silent exactly when it fires. A missing canary script or absent `jq` emits `count=1` rather than the usual quiet `count=0`: a critical liveness monitor that cannot run is itself the alarm.
  - One tool call per server invocation, which is not an aesthetic choice. `@modelcontextprotocol/server-memory` 0.6.3 serves pipelined stdio requests concurrently and every mutation is a lock-free read-modify-write of the whole graph file, so `delete_entities` and `create_entities` sent down one pipe can both `loadGraph()` before either saves - the create then sees the entity still present, filters it out as already-existing and creates nothing while reporting success. Found by running the canary twice against Sean's live install: the first run passed (nothing to delete), every run after it failed. Process exit is the only ordering barrier available without a stateful JSON-RPC client.
  - `_memory-graph.sh` extracts the `.mcp.json` graph-path resolution out of `bootstrap-audit.sh` so the install-time reachability check and the continuous canary cannot drift apart on where the graph lives.
  - `health:` is now a reserved, monitor-owned entity namespace, documented as excluded from recall in `CLAUDE.md.template` and `memory/WRITING_RULES.md`. The exclusion is documentation-level; `server-memory` has no way to hide an entity from `search_nodes`.
  - Behavioural suite `test-memory-canary.sh` (wired into `shell-tests.yml`, stubs the MCP server so it needs no network or npx) forces every failure: namespace-invalid absolute path, non-writable graph dir, an empty read after a write the server reported as successful, a write that does not persist, a server that cannot start, and an absent memory block. It also asserts the sequencing directly: three spawns, three distinct PIDs, one tool call each, in that order, plus a second-consecutive-run case.
- **Voice-agent plugin (#138).** Plugin skeleton, manifest, install script, env loading and config extraction. The manifest declares `platform: darwin/arm64` and `runs: host`, because Whisper MLX and Kokoro MLX are Apple Silicon only. The eight source modules were copied in unchanged in the first commit on purpose, so that any regression from the config extraction that followed is attributable to the extraction rather than to the move. Documented separately is why this lives here and not in `behalfbot-plugins`.
- **`gmail-monitor` reads attachments, and no longer returns empty bodies for HTML-only mail.** Two holes in the read surface, both invisible from outside the server. `_extract_plaintext` only ever walked `text/plain` parts, so an HTML-only message came back as `body: ""` with no indication anything had been missed - that is most machine-sent mail. Concretely: a single-use sign-in link returned an empty body and the token had to be reconstructed by hand.
- **Governance: `CONTRIBUTING.md`, `SECURITY.md`, a PR template, `CODEOWNERS` and a DCO check.** The repo is public and had no statement of what a contribution should look like, no private channel for a vulnerability report, and no record of the terms an inbound contribution arrives under. `CONTRIBUTING.md` leads with what the project is NOT, because the most common reason a well-written PR gets declined here is that it makes the chassis more specific rather than more general.

### Fixed

- **`bootstrap-audit.sh` Gap 3 could never pass, so the memory-graph check had never caught anything (#142).** Gap 3 read `.mcpServers.memory.env.MEMORY_FILE_PATH` out of the customer's `.mcp.json`, but the current `.mcp.json.template` deliberately sets no `env` block - it resolves `$(pwd)/memory/memory.jsonl` inside an `sh -c` wrapper, because the host and the chassis container see the same bind-mounted directory at different absolute paths (`/Users/<user>/.behalfbot` vs `/app/customer`) and a single baked absolute path is therefore valid in only one namespace. Every install on the current template reported a false Gap 3 failure, and the check that exists to catch an unreachable knowledge graph could not pass on any of them. Gap 3 now resolves the graph path from either shape - legacy `env.MEMORY_FILE_PATH` when present, otherwise the cwd-resolved `$CUSTOMER_HOME/memory/memory.jsonl` the wrapper produces - and fails only when the resolved graph is unreachable or non-writable.
- **A memory graph whose directory does not exist is now a Gap 3 failure rather than a warning.** That is the original amnesiac-bot symptom (an absolute path baked in one namespace and read in the other), not a nit.
- **`${CHASSIS_HOME:-default}` in a hand-edited `.mcp.json` is expanded.** The old substitution handled only the bare `${CHASSIS_HOME}` token, so the defaulted form fell through as a literal path and failed. Expansion stays scoped to `CHASSIS_HOME` and `CUSTOMER_HOME`: the config is data, not shell to evaluate.
- New behavioural suite `chassis/scripts/test-bootstrap-audit-memory.sh` (wired into `shell-tests.yml`) covers both config shapes and forces every unreachable-graph case - missing dir, non-writable dir, foreign-namespace absolute path, absent memory block - so the fix cannot degrade into a check that passes everything.
- **A chassis update offered once and not answered is no longer muted forever (#146).** `gather-chassis-update-check.sh` Gate 5 was commented as "avoid double-fire within the same week" and implemented with no time component at all: it compared `last-offered.json`'s `.version` against upstream and skipped on a match. The `offered_at` the same script writes on every emit was never read back - `grep -rn "offered_at" chassis/` returned exactly one hit, the write. So a single notification permanently opted the installer out of that version, and `already_offered` was functionally identical to Gate 4's `dismissed` except the installer never chose it. An installer busy the week they were offered an update never heard about it again, on every install, not just the one where it surfaced. Gate 5 now reads `offered_at` and re-offers once it is older than `CHASSIS_UPDATE_OFFER_COOLDOWN_DAYS` (default 6). Gate 4 is unchanged and stays permanent: an explicit `skip update` is the installer's deliberate opt-out, and an unanswered notification is not a dismissal.
- **The cooldown default is 6 days rather than 7, deliberately.** The heartbeat is `weekly monday 09:00` and the dispatcher fires at the first 15-minute tick at or after that time, once per day-of-week, so consecutive checks land ~7 days apart give or take tick alignment and DST. A 7-day window races that: a tick a few minutes "early" leaves the delta just under the window, the check stays silent, and the once-per-day-of-week guard pushes the next attempt out a full week. The weekly re-nag would silently become fortnightly. Six days clears before every weekly tick.
- **Timestamp handling fails open.** An absent, unparseable or future-dated `offered_at` re-offers rather than staying silent, because silence is the failure mode the gate exists to stop. The empty-string case is guarded explicitly: GNU `date -u -d "" +%s` returns midnight today with exit 0, so a state file missing `offered_at` would otherwise have resolved to "offered today" and muted. Caught by the new suite running under GNU date in the chassis container after passing under BSD date on the host.
- New behavioural suite `chassis/scripts/test-chassis-update-check.sh` (wired into `shell-tests.yml`, no docker and no network - upstream is served from a temp dir over `file://` through the existing `CHASSIS_UPDATE_RAW_BASE` override) covers all five gates in 23 cases, including cooldown boundaries at the default window, the env-var override in both directions, dismissal outranking an expired cooldown, and every fail-open path. Seven of its cases fail against the pre-fix script, so the suite is proven to catch the defect rather than merely to pass.
- **`bake-env.sh` refuses a bake that collapses the key count.** It derives its key set by diffing the environment before and after sourcing `.env`, so any variable already present in the calling shell is subtracted out. Run it from a shell that has already sourced `.env` - easy to do by accident, since `bw-unlock.sh` and several gather scripts do exactly that - and it quietly wrote an almost-empty file while reporting success.
- **The dispatcher locks the state-file read-modify-write cycle, not just the temp path.** `set_state` and `increment_fire_count` shared one `${STATE_FILE}.tmp` staging path with no locking. A unique temp path per writer, which was the originally scoped fix, does not actually close the race.
- **`validate-heartbeats` strips env-prefixed gather args before resolving the path.** `gather_path="${value%% *}"` stripped trailing inline args but not a leading `KEY=VALUE` prefix, which is the documented way to parameterise a shared chassis gather per heartbeat. Such a heartbeat resolved its gather path to the env token and was permanently flagged as missing.
- **`daily-log-gather` day filters are exclusive on the upper bound.** `since_str <= x <= until_str` made every PR or issue event from "today" count as yesterday's work too, since the report's date field is `since_str`. A PR merged at 00:30 UTC landed in both days' logs.
- **`merge-plugin-triggers.sh` resolves plugins via `CHASSIS_PLUGINS_ROOT`.** It read manifests from `$CHASSIS_HOME/plugins/<name>` only, never the baked-plus-fetched overlay every other plugin-tree consumer uses (#95). In-container that path resolves to the customer-side `plugins/` dir, so a plugin fetched or baked into the chassis tree installed and validated cleanly but never got its Discord trigger registered, silently.
- **`diff-against-canonical` runs on every PR.** It is a required status check, and a path-filtered workflow never reports on a PR outside its paths, so branch protection blocked such PRs indefinitely on "Expected - Waiting for status to be reported". No red X, no log, nothing for a contributor to click.
- **`shell-lint` excludes the second zsh file (#144).** `test_state_write_race.sh` carries a `#!/bin/zsh` shebang and shellcheck has no zsh support, so it failed SC1071 while `ignore_names` listed only `heartbeat-dispatcher.sh`. "Shell scripts lint" had been red on `main` since 2026-08-02.

## v0.4.0 - 2026-07-28

### Added

- **The boot-time chassis-root resolution (#118) is now monitored on a schedule, and a `behalfbot` container that is DOWN or restart-looping now pages (#119).** #118 resolves the effective chassis tree once at container boot and records the outcome in `$CUSTOMER_HOME/chassis-root.state.json`, but nothing re-checked it - the same "a check that exists but never fires is not monitoring" defect class as the SiYuan MCP stale-config incident. Two new chassis-generic, default-on heartbeats close the gap:
  - `gather-chassis-root-health.sh` + `chassis-root-health-prompt.md` (every 30m, `critical`) re-reads the state file each tick and fires when either failure mode is present: **silent staleness** (the runtime resolved `baked` while a usable live tree now exists at `$CUSTOMER_HOME/chassis/chassis` - the exact drift #118 exists to prevent, re-appearing if the mount was absent at boot then restored without a restart) or a **loud-fail assertion** (the resolver hit an exit-5 path - torn live tree, MAJOR skew, or symlink-materialisation failure - recorded in the state file's `error`). Near-free (a file read + a live-tree usability probe replicating the resolver's `usable()` guard; no docker, no network). Degrades to a clean no-op on any pre-#118 install where the state file is absent (nothing resolved yet cannot have drifted) and stays silent on a deliberate operator override (`mode: explicit`). Emits no secrets - chassis roots are container paths and versions are semver strings.
  - `gather-container-liveness.sh` + `container-liveness-prompt.md` (every 15m, `critical`, opt-in - needs the docker socket) `docker inspect`s the core stack containers (`CHASSIS_LIVENESS_CONTAINERS`, default `behalfbot,behalfbot-postgres`) and fires on `_down_<status>`, `_restarting`, `_restart_loop` (RestartCount delta since the previous tick, persisted in a state file), `_absent`, or `_unhealthy`. This catches the case `gather-service-health.sh`'s HTTP probe structurally cannot: the primary `behalfbot` container serves no endpoint, so its liveness was never checked, and #118's exit-5 boot abort can crash-loop it. Docker-unreachable is a deliberate no-op so socket-less installs never false-alarm. Structural caveat documented in the prompt: the dispatcher runs INSIDE `behalfbot`, so the in-container heartbeat catches sibling-down + `behalfbot` restart-loops but not a fully-dead `behalfbot`; the SAME location-agnostic script wired into a host LaunchAgent / systemd timer against the host daemon covers that within one interval.
  - Behavioural suites `test-chassis-root-health.sh` and `test-container-liveness.sh` (both wired into `shell-tests.yml`, no docker daemon) force every alert condition and assert it fires - per the "checks that cannot fail" rule, each monitor is proven to fire before it is trusted - and assert silence on every healthy / unknown state.

### Fixed

- **The runtime now resolves the operator's LIVE chassis tree instead of silently running the stale image-baked copy.** A containerized install carries two chassis trees: `/app/chassis` baked into the image at build time, and the operator's live git tree when the install bind-mounts its clone at `$CUSTOMER_HOME/chassis` (or vendors the repo as a subtree there; both layouts nest the tree at `$CUSTOMER_HOME/chassis/chassis`). `CHASSIS_ROOT` was baked as Dockerfile ENV pointing at the baked copy, so `git pull` updated the disk while every consumer of `CHASSIS_ROOT` - `bootstrap-mcp-config.sh` and the `.mcp.json.template` it renders, gather scripts, `first-boot-announce.sh`, the dispatcher default - kept executing code from releases ago. The operator believed the install was updated; it was not. Confirmed concretely on the reference install: baked tree at v0.2.0 (no `gmail-monitor-mcp.py`, no `reconcile-mcp-config.py`, pre-#114 template), mounted tree current, and a `--force` re-hydrate would have emitted a `gmail-monitor` entry pointing at a script that does not exist in the tree the runtime resolves. Same defect class as the v0.2.0 fetched-plugins no-op (#82), applied to the chassis itself. Now:
  - New `chassis/scripts/resolve-chassis-root.sh` resolves the effective root at container boot: a pre-set `CHASSIS_ROOT` is an operator override honoured verbatim; otherwise a USABLE live tree at `$CUSTOMER_HOME/chassis/chassis` wins (even when older than baked - that is what a rollback looks like); otherwise the baked tree. Whole-tree preference, not a per-file overlay: the chassis is one coherent versioned unit and mixing files across versions is worse than choosing one tree. A live tree that exists but is torn (missing `VERSION`, `scripts/`, or the dispatcher), or whose MAJOR differs from the baked MAJOR (MAJOR is reserved for image-contract changes), forces baked LOUDLY - exit 5, ERROR in the boot log, error recorded in the new `$CUSTOMER_HOME/chassis-root.state.json`.
  - The Dockerfile no longer bakes `CHASSIS_ROOT` as ENV, for exactly the reason `CHASSIS_PLUGINS_ROOT` stopped being baked: a baked value is indistinguishable from an operator override and makes the resolver unreachable. The entrypoint resolves after `source_env` in every mode and exports the result to the whole supervised process tree (dispatcher, `claude -p`, MCP servers, one-shot modes). Migrations and `bootstrap` now run against the resolved tree's parent instead of a hardcoded `/app`.
  - The resolved root is materialised as a symlink at `$CUSTOMER_HOME/state/chassis-root` and `_env.sh` consults it first when `CHASSIS_ROOT` is unset, so `docker exec` sessions (which never inherit the entrypoint's exports) see the same tree the dispatcher runs. `chassis-update.sh`'s post-update healthcheck reads the container version through that symlink first, which also closes a publish-lag hole: after a `git pull` + restart the healthcheck converges on the live tree's version even when the GHCR `latest` image build is still catching up.
  - `smoke-test.sh` gains `check_chassis_root_resolution`: FAILs whenever a usable live tree is present but the running `CHASSIS_ROOT` is a different tree - the "operator updated, runtime did not" state can no longer pass a smoke test. Behavioural suite in `test-chassis-root-resolution.sh` (wired into shell-tests CI) locks down live-wins, torn-tree exit 5, MAJOR-skew refusal, override verbatim, rollback semantics, symlink retargeting, and the `_env.sh` docker-exec path.
  - Blast radius: installs that do not mount a chassis tree resolve baked and behave exactly as before. Existing installs need ONE image refresh (`compose pull` + `up -d`, or the next `chassis-update.sh` run) to pick up the resolving entrypoint; from then on chassis updates take effect on container restart without waiting on an image rebuild.

- **Dating: a PIN-locked AVD can no longer pass readiness, and recovery unlocks it instead of restart-looping.** An AVD with a lock-screen PIN cold-boots into user state `RUNNING_LOCKED`: Android is up, but the credential-encrypted user is never unlocked, so no dating app's activities are registered. Every readiness signal the automation trusted is TRUE on that device (adb attached, `boot_completed=1`, non-zero screencap, packages installed, window focus non-null - the keyguard holds focus), so monitors reported it healthy while `resolve-activity` found nothing to launch. Worse, the unlock transition produces transient bad readings (0-byte screencap, null focus) that watchdogs read as a wedged GPU - killing the emulator mid-unlock, booting it back locked, and declaring the lock screen ready. Now:
  - New shared probe `plugins/dating/scripts/emulator-state.sh` emits a machine-readable state token (`emulator_not_running`, `emulator_not_booted`, `emulator_locked`, `emulator_no_focus`, `emulator_apps_unresolvable`, `emulator_ready`). Readiness requires `dumpsys user` NOT `RUNNING_LOCKED` and every package in `emulator.required_packages` resolving a launcher activity.
  - The recovery hook routes per state: locked devices get a PIN unlock in place (wake, swipe up, type PIN, enter, poll for `RUNNING_UNLOCKED`), never a restart - a restart boots a PIN-locked AVD straight back to the lock screen. The post-restart wait loop also unlocks, so a cold boot ends ready instead of "successfully" locked. Wedge signals must persist across two samples before any kill, and the hook stands down while an unlock is in flight. `-wipe-data` is explicitly out of bounds as automated recovery for a locked device - it logs the installer out of every dating app.
  - The PIN comes from the env var NAMED by new manifest field `emulator.pin_env_var` (default `DATING_EMULATOR_PIN`) - the installer wires that var to their own secret store; the PIN never appears in config, the repo, or logs. Locked device + unset var is a loud, immediately-alerted error naming the var, not a silent skip.

## v0.3.0 - 2026-07-21

The release that makes v0.2.0 real. The plugin fetcher shipped in v0.2.0 downloaded and verified a plugin tree that the chassis then never used; this release makes the fetched tree actually take effect, as an overlay rather than a swap. Also hardens the Notion and Obsidian second-brain adapters to the point where full-length documents survive a round trip, and removes nationality-based screening from the public dating plugin.

### Second brain

- **Notion accepts documents longer than 100 blocks.** `create_doc` and `append_to_doc` chunk into batches of at most 100 and issue a create followed by sequential appends. Previously any document over roughly 100 non-empty lines returned `HTTP 400: body.children.length should be <= 100`, which meant a full-length briefing could not be written at all.
- **Long paragraphs are no longer silently truncated.** Notion caps a single `rich_text` field at 2000 characters. The old code cut the content and reported success; it now splits across parts. This was losing text with no error.
- **Notion rate limiting is handled.** `_request` honours `Retry-After` (seconds or HTTP-date) with a bounded retry count. Only 429s are retried - Notion's limiter rejects before executing, so a retry cannot double-write. 5xx and network errors are deliberately not retried, because the write may have landed.
- **Chunked writes report partial failure precisely.** A failed chunk raises with the page id plus how many chunks of how many landed, so a retry is not blind. Partial content is left in place; a rollback delete can itself fail, and an append cannot distinguish its own blocks from pre-existing ones.
- **Obsidian frontmatter.** Optional YAML frontmatter on write, and frontmatter stripped from `search`/`list_recent` snippets so existing notes stop returning metadata noise. Templater and Dataview content round-trips unchanged.
- **Obsidian daily notes.** New `second_brain.obsidian.daily_notes_dir` config plus helpers, so briefings and daily-log output land where the Daily Notes plugin expects them.
- **Test coverage for the Notion adapter**, which was the only adapter with none.

### Plugins

- **The fetched plugin tree is now actually used.** v0.2.0 claimed `CHASSIS_PLUGINS_ROOT` preferred `$CUSTOMER_HOME/vendored-plugins`. It never did: the preference lived in `_env.sh` behind an is-unset guard, while the Dockerfile ENV and `docker/entrypoint.sh` both set the variable before `_env.sh` could run. The fetch worked, the lockfile was written, and every install silently kept loading the baked tree.
- **Resolution is an overlay, not a swap.** A plugin present in the fetched tree wins by name; anything only in the baked tree still loads. The v0.2.0 design, had it been reachable, would have taken every install from 7 plugins to the 1 currently published in `behalfbot-plugins`. A fetched directory without an `openclaw.plugin.json` never shadows a baked copy, and a failed fetch degrades per plugin rather than wholesale.
- **A silent no-op is no longer possible.** Boot writes `plugins-root.state.json` with per-plugin provenance, and if a usable fetched tree exists but is not active the resolver exits 5 and the entrypoint logs an unmissable error.

### Dating plugin

- **Nationality-based screening removed from the public plugin.** The shipped defaults enabled a regional default-reject gate with a populated country list, and the documented triggers included ethnic self-identification and script detection. Those are identity attributes, not behaviour. The gate mechanism remains for installers who want to configure it; the chassis now ships it disabled with an empty list and names no countries.
- **Behavioural fraud signals are now the primary path** - reverse-image consensus, photo sets found on aggregator sites, a digital footprint concentrated on one national internet with no corroboration elsewhere, refusal of verification. These are more accurate than a country list, which flags genuine expats and misses catfish operating from anywhere else.
- `pimeyes_russian_internet_only_presence` renamed to `pimeyes_single_country_footprint_only`. The old key remains a defined deprecated alias that is honoured with a loud warning - the schema sets `additionalProperties: false`, so removing it outright would have invalidated existing configs, and a renamed safety setting that silently reverts to default is a safety regression.

### v0.3.0 detail - plugin root

### Fixed
- **v0.2.0's plugin-root preference never ran.** The Changed entry below ("`CHASSIS_PLUGINS_ROOT` now prefers `$CUSTOMER_HOME/vendored-plugins`") described behaviour that was unreachable in every container: the preference lived in `_env.sh` behind an is-unset guard, but the Dockerfile ENV baked `CHASSIS_PLUGINS_ROOT=/app/plugins` and `docker/entrypoint.sh` defaulted and exported the same value before `_env.sh` could ever run. The fetch worked, `vendored-plugins/` and `plugins.lock` were written, and every install silently kept loading the baked tree. Verified empirically on a live 0.2.0 install (dispatcher env showed `/app/plugins` while a usable fetched tree sat ignored). The "verified in a container both ways" claim in the v0.2.0 notes covered the fetch and the loader's selection logic in isolation, not the boot path that preloads the variable.

### Changed
- **Plugin root is now an overlay, not a tree swap.** `chassis/scripts/resolve-plugin-root.sh` (new) resolves plugins per plugin NAME: a plugin present in the fetched `vendored-plugins/` tree wins, anything only in the baked tree still loads. This replaces the v0.2.0 wholesale preference, which - had it been reachable - would have shrunk every install from 7 plugins to the 1 currently published in `behalfbot-plugins`. The result is materialised as a composed symlink root at `$CUSTOMER_HOME/state/plugins-root` so every existing single-root consumer (entrypoint `install-plugin`, `smoke-test` enumeration, plugin script paths) works unchanged. Per-plugin safety is kept: a fetched dir without an `openclaw.plugin.json` never shadows the baked copy, and an empty or failed fetch degrades to baked per plugin.
- `CHASSIS_PLUGINS_ROOT` is no longer baked as Dockerfile ENV or defaulted by the entrypoint. A set value now reliably means an operator set it (compose environment, `docker -e`, or the customer `.env`) and is honoured verbatim with no overlay. The chassis default path is "unset", resolved at boot.
- Boot now logs the resolved plugin root and writes `$CUSTOMER_HOME/plugins-root.state.json` (mode, source roots, per-plugin provenance). If a usable fetched tree exists but is not active, the resolver exits 5 and the entrypoint logs an unmissable ERROR - the v0.2.0 silent no-op class cannot recur quietly.

### Added
- `chassis/scripts/test-plugin-root-resolution.sh` + CI job `plugin-root-resolution` in `shell-tests.yml`: behavioural tests asserting the resolved root actually serves the fetched copy when a fetched tree is present. The pre-existing tests and CI were green throughout the period the feature did nothing.

## v0.2.0 — 2026-07-20

Plugins move from image-baked to fetched-at-boot. This is the release that makes `behalfbot-plugins` real: the chassis now pulls its plugin tree from that repo at a pinned tag+SHA instead of carrying whatever was baked into the image.

### Added
- `chassis/PLUGINS_PIN` — single line `<tag> <40-hex-sha>` recording the pinned plugin release. Currently `v0.1.0 7f826679d73f3b507e1472c920709766e159bc5e`.
- `chassis/scripts/fetch-plugins.sh` — seed copy of the canonical fetcher from `behalfbot-plugins`. Resolves the pinned tag, **requires the resolved SHA to equal the pinned SHA**, installs into `$CUSTOMER_HOME/vendored-plugins`, and writes `$CUSTOMER_HOME/plugins.lock`.
- Boot-time fetch: `docker/entrypoint.sh` calls the fetcher from `dispatcher` and `bootstrap` modes.
- CI workflow `fetcher-seed-matches-canonical` — fails the build if the chassis seed drifts from canonical.
- `plugins.lock` now records a `skipped[]` array naming any plugin held back by `min_chassis_version`.

### Changed
- **`CHASSIS_PLUGINS_ROOT` now prefers `$CUSTOMER_HOME/vendored-plugins`** over the baked `/app/plugins`, falling back to baked when no fetched tree is present. The fetched tree is only selected if it actually contains at least one `*/openclaw.plugin.json` — an empty or half-written directory must not shadow the baked tree and leave the chassis silently loading nothing.

### Fixed
- `min_chassis_version` in `registry.json` was declared and never evaluated. A plugin requiring a newer chassis installed silently and failed later at runtime. It is now enforced: too-new plugins are skipped individually (the rest of the tree still installs), logged per plugin, and recorded in the lockfile.
- The chassis fetcher seed was committed non-executable, so the boot hook's `[[ -x ]]` guard skipped it and the fetch never ran. Every other artifact was correct and completely inert. Caught by booting a built image rather than trusting green CI — `diff` compares content and ignores mode, so the drift check passed on an unrunnable file.

### Why this bump matters operationally

`loom-vision` declares `min_chassis_version: 0.2.0`. On `0.1.1` the fetch succeeds and **skips** it, leaving `vendored-plugins` without any plugin manifest, so the loader correctly stays on the baked tree. At `0.2.0` the plugin installs and the loader flips to the fetched tree. Verified in a container both ways before this bump.

### Migration

None required. The first boot after upgrading fetches the pinned tree and writes `vendored-plugins/` and `plugins.lock` alongside existing state. Nothing is removed. If the fetch fails for any reason the chassis continues on the baked tree, so a network-isolated install is unaffected.
