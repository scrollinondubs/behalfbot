# Chassis Changelog

Single source of truth for chassis releases. Read by the auto-updater (issue #33) to surface diffs and detect breaking changes.

## Format conventions

Each release is a `## vX.Y.Z` heading. Under it:

- **Added** / **Changed** / **Fixed** / **Removed** subsections (any subset)
- **BREAKING CHANGES:** marker (uppercase, on its own line) when a release requires manual review before applying. The auto-updater notification flips into `--force` mode whenever this marker appears for an unreleased version between the customer's `current` and `latest`.
- **Migration:** subsection pointing at `scripts/chassis-migrations/vX.Y.Z.sh` if the bump needs a state migration. Migration scripts are strictly automated shell scripts only (no Claude judgment, no LLM calls). Judgment-heavy migrations get flagged as BREAKING CHANGES and gated behind explicit operator review.

Semver:

- `MAJOR` (`1.0.0` → `2.0.0`): always BREAKING. Reserved for chassis architecture changes (Docker image base, dispatcher API, subtree layout).
- `MINOR` (`0.3.0` → `0.4.0`): new features, optional fields, opt-in behaviors. Backwards-compatible.
- `PATCH` (`0.3.1` → `0.3.2`): fixes, prompt tweaks, internal refactors. Always backwards-compatible.

## Unreleased

### Added

- **Credentials now warn before they expire, and the warning does not depend on the credential (new-jaxity#550).** Between 2026-09-01 and 2026-09-05 the reference install's operator was off-grid and four credentials expired within days of each other. The Tailscale node key hit its 180-day default expiry on ~09-01, and because the ssh hostname resolves to the Tailscale IP that killed ssh and VNC in one move. The same morning at ~10:06Z the macOS Keychain entry `Claude Code-credentials` lost `claudeAiOauth.accessToken`, killing the HOST interactive Claude session while the container carried on fine - it reads `~/.claude/.credentials.json` and refreshes off the refresh token - so scheduled work kept running, and kept spending, while the terminal was dead. An iCloud trust token went on 09-04. Every channel for reporting any of it depended on one of the four. Nothing warned for four days.
  - New `gather-credential-expiry.sh` + `credential-expiry-prompt.md`, registered in `HEARTBEATS.md.template` as a default-on `every 1h` heartbeat at `criticality: critical`. Free: no model call, no paid API, no network beyond a local `tailscale status`. Built-ins cover the Tailscale self key AND every peer with a key expiry (the laptop or phone whose key dies is the operator's way back in), the macOS Keychain entry, `~/.claude/.credentials.json`, and a token-refresh liveness check. `BackendState: NeedsLogin` is graded `expired` rather than skipped, because that is what an expired node key actually looks like from the CLI; a null `Self.KeyExpiry` is graded `ok`, because expiry-disabled is the correct configuration for an always-on host and a check that nagged about it would be muted inside a week.
  - **Watching the credentials FILE would have shown green through all four days.** The Keychain is a separate store with a separate failure mode, and the container's health said nothing about the host's. Both are checked, separately, and the Keychain losing its token alerts on the FIRST occurrence with no threshold at all.
  - **The access token deliberately does not get the T-7 / T-1 ladder.** It lives about an hour and refreshes itself, so a day-based threshold on it alerts permanently. `refreshTokenExpiresAt` gets the ladder; the access token only produces a finding when the newest one across both stores has sat expired past a grace window, which means every refresh path is dead.
  - **Repeat suppression is per-check and keyed on the STAGE, never the day count.** A fingerprint carrying a volatile counter never matches its own previous value, so the cooldown never applies and the alert fires on every tick - a defect this codebase has shipped before. T-7 fires once and goes quiet; T-1 fires on the transition; `expired` / `missing` / `unknown` re-nag on a 3-day cooldown because they do not self-resolve and an unanswered notification is not a dismissal; `t7` never re-nags, since a 3-day re-nag on it would fire again at T-4. Per-check rather than per-run state is also what lets the host runner and the in-container heartbeat coexist without alternating.
  - **The heartbeat alone is not enough on a containerized install, and the docs say so rather than implying coverage that is not there.** The dispatcher runs inside the container, where there is no macOS Keychain and no tailscaled, so the two checks that would have caught this outage are host-only. And the heartbeat's delivery path is `claude -p` while one of the watched credentials is Claude's own. New `credential-expiry-alert.sh` runs the same gather from a host LaunchAgent and posts straight to the ops webhook with no model in the loop. `chassis/docs/heartbeats/credential-expiry.md` carries the coverage table, the LaunchAgent-not-LaunchDaemon wiring (a Background-session job cannot unlock the login keychain, and would report the Keychain check as a permanent false `unknown`), and the drop-in contract.
  - **Installs extend it without touching `chassis/`.** Any executable in `${CUSTOMER_HOME}/scheduled-tasks/credential-checks.d/` is run and its JSON merged - epoch seconds, epoch milliseconds or ISO8601 expiries, or an explicit state when the script would rather decide for itself. A drop-in that exits non-zero or emits garbage is reported as `unknown` rather than dropped: a credential check that cannot run is a credential nobody is watching.
  - Emits no secrets. Presence, epochs, hostnames and states only, asserted directly by the suite, because the dispatcher logs gather stdout verbatim.
  - Coverage: `test-credential-expiry.sh`, 58 cases, wired into `shell-tests.yml`. Nine of them fail against a build that puts `days_remaining` back into the fingerprint and the state record, so the suite is proven to catch that defect rather than merely to pass.
- **New `_alert.sh`: one way to tell the operator something without a model.** Three delivery paths, first one that works wins: `$CHASSIS_ALERT_CMD`, then `post-to-channel.sh $CHASSIS_ALERT_CHANNEL` (webhook, default channel key `ops`), then `discord-post.sh` with `DISCORD_BOT_TOKEN` and a channel ID resolved from `$CHASSIS_ALERT_CHANNEL_ID` / `DISCORD_ALERTS_CHANNEL_ID` / `DISCORD_OPS_CHANNEL_ID` / `DISCORD_PRIMARY_CHANNEL_ID`. It also supplies the `CHASSIS_HOME` fallback a launchd job does not have, and sources the install's `.env` inside a subshell so a caller under `set -euo pipefail` cannot be killed by a file it does not control.
  - **The bot-token path is not redundant.** An install can have a bot token and channel IDs and no webhook URL at all; the reference install is exactly that shape, which is also why the dispatcher's own `alert_ops()` has been dropping alerts there with `WARN: no ops webhook set`. A helper that stopped at the webhook would be one more monitor firing into a log.
  - Deliberately no state, no dedupe and no formatting opinions: repeat suppression belongs to the caller, which is the only layer that knows what "the same alert" means.

### Fixed

- **The oauth bridge detected the Keychain token loss and told nobody, 288 times (new-jaxity#550).** `sync-claude-oauth-bridge.sh` has always had the right check. Between 2026-09-01 and 2026-09-05 it wrote `WARN: keychain JSON missing claudeAiOauth.accessToken` 288 times into `logs/scheduled/claude-oauth-bridge-sync.log` - 48 a day is the ceiling for a job running every 30 minutes, and three consecutive days hit it - while the host interactive session was dead and the operator was off-grid. Same failure shape as a heartbeat posting into a channel nobody can act on: the detection was never the missing piece, the delivery was.
  - Both WARN paths now post once, on the first tick after a healthy state, and then stay silent until the condition clears - at which point they post a recovery notice. Edge-triggered, not level-triggered: 288 identical webhook messages would be exactly as useless as 288 identical log lines, and would have got the channel muted.
  - `keychain_unreadable` and `keychain_missing_token` stay distinct conditions, because they need different fixes. A refused read usually means the caller is in launchd's Background session and cannot unlock the login keychain, which is a launchd-domain problem, not a re-login.
  - The recovery check sits on the healthy boundary, above the reverse-sync and identical-hash early exits. Both of those `exit 0` on a perfectly healthy keychain, so a recovery notice placed below them would never post on the common path.
  - Delivery goes through `_alert.sh` (webhook, no model), because the credential in question is Claude's own. The condition is recorded whether or not delivery succeeded: an install with no webhook configured would otherwise retry every 30 minutes forever, which is the noise being removed. The failure is logged instead, and alerting never breaks syncing.
  - The per-tick WARN log line is retained. It is the forensic record that dated this outage to the minute.
  - **The `source` of `_alert.sh` is guarded, and the guard is load-bearing.** This script runs under `set -euo pipefail` every 30 minutes and is the only thing keeping the container authenticated. An unguarded `source` of a sibling would have killed the sync outright on any install running a copy of it from elsewhere - making the most critical script in the install more fragile, in a change about resilience. A missing helper degrades to the old log-only behaviour instead, and the suite proves an orphaned copy still syncs and still logs.
  - Coverage: `test-claude-oauth-bridge-alert.sh`, 36 cases, wired into `shell-tests.yml`. 19 fail against the pre-fix bridge, and 6 more against a build with the source unguarded and the bot-token path removed. The suite clears both bars deliberately - that the fault alerts at all, and that it does not alert 287 more times - because a fix that swapped a silent log for 288 webhook messages would be the same failure wearing a different hat.

- **A wrong parameter name on the Discord reply tool silenced an install for four hours (#511 customer-side).** The reply tool's body parameter is `text`. A call passing `message` arrives with `text` undefined and dies inside the plugin's own `chunk()` splitter with `reply failed: undefined is not an object (evaluating 'text.length')`. The error names a plugin internal rather than the parameter, so the failure reads as a plugin fault: the reference install spent an hour reading plugin source on 2026-08-13 while its installer received nothing, and the terminal transcript looked healthy throughout. Anthropic's Discord plugin is the real root - it could accept `message` as an alias, or raise an error that names the field - but every install running that plugin can hit this today.
  - New `chassis/.claude/hooks/discord-reply-param-fix.sh` renames the key in flight via `hookSpecificOutput.updatedInput`. It is a PreToolUse hook that **denies nothing**, which is new for this layer; `docs/security.md` gains a section distinguishing correctness rewrites from the safety blocks so the two are not confused.
  - **Silence on the common path is the safety property, not a nicety.** This hook fires ahead of every Discord reply, so a hook that emits an `updatedInput` when none is needed is a hook rewriting payloads it does not understand. Correct calls produce no output at all.
  - **Every `jq` in it fails open.** A non-zero exit from a PreToolUse hook can block the call, and a hook that mutes the Discord channel on malformed stdin defeats its own purpose. The first draft did not: `set -euo pipefail` propagated `jq`'s exit 5 on unparseable input, and the test suite caught it before the hook shipped.
  - **`docs/security.md` now documents how hooks are registered at all.** They ship in this repo but are wired host-side in `~/.claude/settings.json`, and that step was written down nowhere - a hook present on disk and absent from that file does nothing, with nothing to surface the gap.
  - Coverage: `test-discord-reply-param-fix.sh`, 24 assertions, wired into `shell-tests.yml`. Proves the rewrite carries `chat_id` / `reply_to` / `files` across (a rewrite that drops the attachment list turns a loud failure into a quiet one), that a multiline body with quotes and backslashes survives the round trip byte for byte, that all six non-bug paths stay silent, and that malformed and empty stdin exit 0.

- **The update path was blind to every merge that landed under an unchanged `VERSION` (#147).** `chassis/VERSION` moves only on an explicit release commit, but `main` is the distribution branch: `chassis-update.sh` hardcodes `UPSTREAM_BRANCH="main"`, and the latest release tag was `v0.1.1` while `VERSION` read `0.5.0`. Both `gather-chassis-update-check.sh` and `chassis-update.sh` gated on string equality between local and upstream `VERSION`, so the moment those matched, the checker emitted `{"count": 0, "reason": "up_to_date"}` forever and the applier answered `update chassis` with "Already up to date. Exiting." On 2026-08-09 the reference install sat nine commits behind an upstream reporting the same version number, including #142's fix for a `bootstrap-audit.sh` check that could never pass, while a bug had been silently destroying its knowledge graph for sixteen days. Cutting v0.5.0 unblocked that install; this stops it recurring, there and on every install that tracks `main`.
  - The signal is a digest of the `## Unreleased` section, compared **local tree against upstream** rather than upstream against a stored baseline. Local-versus-upstream measures the condition that matters ("this tree differs from what an apply delivers") instead of a proxy ("upstream moved since we last said something"), needs no seeding - a stored baseline has a cold start where the first run after shipping either fires on every install or silently records an already-drifted install as level, which is the failure being fixed - and self-clears after an apply with no state write. New shared `_chassis-changelog.sh`, sourced by both the checker and the applier so they cannot disagree on what drift is.
  - **The gap is named rather than hidden: a merge that lands code and adds no changelog entry moves no digest and stays invisible.** The durable complement is requiring a changelog entry per PR, which is CI work and a separate issue. Keying on the upstream commit SHA for `chassis/` via the GitHub API was considered and rejected: exact, but it puts an authenticated-or-rate-limited dependency into scripts that today need neither.
  - **The emitted JSON now carries an explicit `kind`**, `version` or `drift`, because a drift offer has `current == latest` and both consumers - `chassis-update-check-prompt.md` and the `chassis-update` skill - were written assuming otherwise. Both handle the drift shape; a notification the apply path cannot act on would be worse than no notification.
  - **The applier had three separate blockers, not one.** Beyond the version-equality gate, the post-pull check died with "pull did not advance the chassis tree" - true of every drift apply by definition - and the healthcheck compared `VERSION`, which for drift passes on the first poll whether or not anything happened, the exact tautology `_chassis-update-health.sh` exists to warn about. All three now take the digest as evidence, including a `docker exec` read of the container's own `CHANGELOG.md` digested host-side. Migrations are skipped on a drift apply: `vX.Y.Z.sh` already ran when that version was applied.
  - **`dismissed.json` is now keyed per offer.** `skip update` on a drift offer writes `<version>+<digest>`, so the next merge under the same version is still surfaced; a bare version string keeps its old meaning of muting that version entirely, which is what every entry written before this change means and what `skip update` on a version offer still writes.
  - **The `BREAKING CHANGES:` window now includes `## Unreleased`**, for version offers too. A pull of `main` delivers the unreleased commits along with the released ones, so a marker sitting under `## Unreleased` was being applied while the notification said no review was needed. Capture deliberately starts at the `## Unreleased` heading rather than the top of the file, because the format-conventions preamble above it contains the literal marker text.
  - **Cost contract changed on purpose.** The changelog GET moves above the up-to-date gate, so the common path is two unauthenticated `raw.githubusercontent.com` requests on a weekly heartbeat instead of one. The alternative was keeping a checker that structurally cannot see what it exists to see.
  - Coverage: `test-chassis-update-check.sh` grows from 23 to 46 cases and `test-chassis-update-mode.sh` from 42 to 54, the latter including real `git pull` runs against a local bare repo because two of the three applier blockers are unreachable from `--dry-run`. Run against `origin/main`'s scripts, 20 and 12 of those cases fail respectively, so the suites are proven to catch the defect rather than merely to pass.
- **The memory canary's own wrapper could not find it (#151).** `gather-memory-canary.sh` derived the canary's path from `CHASSIS_HOME` (`${CHASSIS_HOME}/chassis/scripts/memory-canary.sh`). That names the chassis tree only on a host-side install. Inside the container `CHASSIS_HOME` is the CUSTOMER root, so the path resolved to `/app/customer/chassis/scripts/`, which exists on neither container shape - not the baked layout (`/app/chassis`) and not the mounted-clone layout (`/app/customer/chassis/chassis`). On the reference install the canary passed by hand while the gather wrapping it reported `count=1, stage=unavailable`: the monitor calling itself dead. Wired at `criticality: critical`, that pages daily about a monitor that is working.
  - The gather now resolves the canary from its own `SCRIPT_DIR` first (they ship in the same directory, so a sibling cannot be the wrong tree), falls back to `chassis-root.state.json` read the way `gather-chassis-root-health.sh` reads it, and only then to the legacy host layout. The unavailable message now names every location searched instead of one.
  - `gather-bootstrap-audit.sh` carried the same idiom and the same consequence, quieter: it emits `count=0, "cannot gate"` when the audit is missing, so the bootstrap audit has silently never run on a containerized install. Same resolver, same order; its quiet-on-missing contract is unchanged, because that gather is not `criticality: critical`.
  - **The registration in `HEARTBEATS.md.template` was wrong in a second, independent way.** Its `gather:`/`prompt:` convention is `${CHASSIS_HOME}/chassis/...` for chassis-shipped files. Gather lines are `eval`ed, so that expands - to a path no container has. Prompt paths are never variable-expanded; the dispatcher joins the raw string onto `$CHASSIS_HOME`, so the templated prompt becomes the literal `/app/customer/${CHASSIS_HOME}/chassis/...` and the heartbeat would have died with `prompt_missing` the first time it fired. Both legs of the memory-canary block now address the boot-time `state/chassis-root` symlink relative to `$CUSTOMER_HOME`, which resolves on both container layouts. The path-conventions section documents the container case and the host-install caveat; the other heartbeat blocks still carry the old idiom and are left for a follow-up.
  - Coverage: `test-memory-canary.sh` gains a chassis root that is not `$CHASSIS_HOME/chassis`, resolved via the state record, plus a stale state record that must still fire rather than pass; `test-bootstrap-audit-memory.sh` gains sibling and offset-root resolution cases for the audit gather. Three of the five discriminate: the two offset-root cases and the audit sibling case fail against the pre-fix scripts. The stale-record and quiet-on-missing cases pass either way by design - they pin behavior the fix had to preserve rather than behavior it introduces.

## v0.5.0 - 2026-08-09

Sixteen commits that had accumulated on `main` under an unchanged `VERSION`. That is not incidental to this release: because both `gather-chassis-update-check.sh` and `chassis-update.sh` gate on string equality between local and upstream `VERSION`, every one of these commits was structurally invisible to every install's update path until this bump. The reference install was nine commits behind an upstream that reported the same version number, including the fix for a bug that had been silently destroying its knowledge graph. See #147.

### Added

- **A silently amnesiac install now pages within a day (#145).** #142/#143 fixed the detector that could never pass; this adds the detector for the failure that actually happened. Sean's memory MCP knowledge graph was unreachable from inside the chassis container for at least sixteen days (2026-07-24 to 2026-08-09) because `.mcp.json` baked an absolute host path that does not exist in the container namespace. Nothing caught it: writes did not error in a way anything collected, and a read from a broken graph returns a well-formed empty result, which is indistinguishable from "no prior context". Gap 3, even after #143, asserts the graph is *writable* - a writable, reachable, completely unused graph passes it clean, which is exactly the state that install was in.
  - `memory-canary.sh` does a write-read-verify round trip: it writes a per-run nonce to the reserved entity `health:memory-canary` using the exact command `.mcp.json` declares, then reads it back **in a separate server invocation** and asserts the two match. The separate read-back is the load-bearing part - a same-process round trip would pass against an in-memory cache while the file path was broken, which is the #142 bug wearing the opposite sign. Separation is structural: three independent process spawns (clear, write, read) sharing nothing but the graph file. Failures name the resolved path, the config shape and the exact error, so the first line of the alert identifies the namespace problem rather than saying "memory broken".
  - Deliberately NOT an mtime staleness threshold. Memory writes are event-driven, so a quiet week is indistinguishable from a broken graph; any threshold either false-alarms or is loose enough that it would not have caught the sixteen-day outage until late. It would also measure a proxy (are writes happening) instead of the property that matters (can this install write and read back its own memory).
  - `gather-memory-canary.sh` + `memory-canary-prompt.md`, registered in `HEARTBEATS.md.template` as a default-on `daily 07:00` heartbeat with `criticality: critical`. The gather ALWAYS exits 0 and carries the verdict in `count`, because the dispatcher treats a non-zero gather exit as count=0 - a gather that exited non-zero on failure would go silent exactly when it fires. A missing canary script or absent `jq` emits `count=1` rather than the usual quiet `count=0`: a critical liveness monitor that cannot run is itself the alarm.
  - One tool call per server invocation, which is not an aesthetic choice. `@modelcontextprotocol/server-memory` 0.6.3 serves pipelined stdio requests concurrently and every mutation is a lock-free read-modify-write of the whole graph file, so `delete_entities` and `create_entities` sent down one pipe can both `loadGraph()` before either saves - the create then sees the entity still present, filters it out as already-existing and creates nothing while reporting success. Found by running the canary twice against Sean's live install: the first run passed (nothing to delete), every run after it failed. Process exit is the only ordering barrier available without a stateful JSON-RPC client.
  - `_memory-graph.sh` extracts the `.mcp.json` graph-path resolution out of `bootstrap-audit.sh` so the install-time reachability check and the continuous canary cannot drift apart on where the graph lives.
  - `health:` is now a reserved, monitor-owned entity namespace, documented as excluded from recall in `CLAUDE.md.template` and `memory/WRITING_RULES.md`. The exclusion is documentation-level; `server-memory` has no way to hide an entity from `search_nodes`.
  - Behavioural suite `test-memory-canary.sh` (wired into `shell-tests.yml`, stubs the MCP server so it needs no network or npx) forces every failure: namespace-invalid absolute path, non-writable graph dir, an empty read after a write the server reported as successful, a write that does not persist, a server that cannot start, and an absent memory block. It also asserts the sequencing directly: three spawns, three distinct PIDs, one tool call each, in that order, plus a second-consecutive-run case.
- **Voice-agent plugin (#138).** Plugin skeleton, manifest, install script, env loading and config extraction. The manifest declares `platform: darwin/arm64` and `runs: host`, because Whisper MLX and Kokoro MLX are Apple Silicon only. The eight source modules were copied in unchanged in the first commit on purpose, so that any regression from the config extraction that followed is attributable to the extraction rather than to the move. Documented separately is why this lives here and not in `behalfbot-plugins`.
- **`gmail-monitor` reads attachments, and no longer returns empty bodies for HTML-only mail.** Two holes in the read surface, both invisible from outside the server. `_extract_plaintext` only ever walked `text/plain` parts, so an HTML-only message came back as `body: ""` with no indication anything had been missed - that is most machine-sent mail. Concretely: a single-use sign-in link returned an empty body and the token had to be reconstructed by hand.
- **Governance: `CONTRIBUTING.md`, `SECURITY.md`, a PR template, `CODEOWNERS` and a DCO check.** The repo is public and had no statement of what a contribution should look like, no private channel for a vulnerability report, and no record of the terms an inbound contribution arrives under. `CONTRIBUTING.md` leads with what the project is NOT, because the most common reason a well-written PR gets declined here is that it makes the chassis more specific rather than more general.

### Changed

- **Plugin pin moved to `behalfbot-plugins` v0.3.0.** Carries Tranche A of new-jaxity#416 - `chef`, `content-research`, `image-generation`, `parse-youtube` and `perplexity-research` - taking the registry from 7 plugins to 12, plus contributor CI and the governance this repo's plugin supply chain had none of. Until the pin moves, `fetch-plugins.sh` resolves the old tag and none of it is reachable.

### Fixed

- **`bootstrap-audit.sh` Gap 3 could never pass, so the memory-graph check had never caught anything (#142).** Gap 3 read `.mcpServers.memory.env.MEMORY_FILE_PATH` out of the customer's `.mcp.json`, but the current `.mcp.json.template` deliberately sets no `env` block - it resolves `$(pwd)/memory/memory.jsonl` inside an `sh -c` wrapper, because the host and the chassis container see the same bind-mounted directory at different absolute paths (`/Users/<user>/.behalfbot` vs `/app/customer`) and a single baked absolute path is therefore valid in only one namespace. Every install on the current template reported a false Gap 3 failure, and the check that exists to catch an unreachable knowledge graph could not pass on any of them. Gap 3 now resolves the graph path from either shape - legacy `env.MEMORY_FILE_PATH` when present, otherwise the cwd-resolved `$CUSTOMER_HOME/memory/memory.jsonl` the wrapper produces - and fails only when the resolved graph is unreachable or non-writable.
- **A memory graph whose directory does not exist is now a Gap 3 failure rather than a warning.** That is the original amnesiac-bot symptom (an absolute path baked in one namespace and read in the other), not a nit.
- **`${CHASSIS_HOME:-default}` in a hand-edited `.mcp.json` is expanded.** The old substitution handled only the bare `${CHASSIS_HOME}` token, so the defaulted form fell through as a literal path and failed. Expansion stays scoped to `CHASSIS_HOME` and `CUSTOMER_HOME`: the config is data, not shell to evaluate.
- New behavioural suite `chassis/scripts/test-bootstrap-audit-memory.sh` (wired into `shell-tests.yml`) covers both config shapes and forces every unreachable-graph case - missing dir, non-writable dir, foreign-namespace absolute path, absent memory block - so the fix cannot degrade into a check that passes everything.
- **A chassis update offered once and not answered is no longer muted forever (#146).** `gather-chassis-update-check.sh` Gate 5 was commented as "avoid double-fire within the same week" and implemented with no time component at all: it compared `last-offered.json`'s `.version` against upstream and skipped on a match. The `offered_at` the same script writes on every emit was never read back - `grep -rn "offered_at" chassis/` returned exactly one hit, the write. So a single notification permanently opted the installer out of that version, and `already_offered` was functionally identical to Gate 4's `dismissed` except the installer never chose it. An installer busy the week they were offered an update never heard about it again, on every install, not just the one where it surfaced. Gate 5 now reads `offered_at` and re-offers once it is older than `CHASSIS_UPDATE_OFFER_COOLDOWN_DAYS` (default 6). Gate 4 is unchanged and stays permanent: an explicit `skip update` is the installer's deliberate opt-out, and an unanswered notification is not a dismissal.
- **The cooldown default is 6 days rather than 7, deliberately.** The heartbeat is `weekly monday 09:00` and the dispatcher fires at the first 15-minute tick at or after that time, once per day-of-week, so consecutive checks land ~7 days apart give or take tick alignment and DST. A 7-day window races that: a tick a few minutes "early" leaves the delta just under the window, the check stays silent, and the once-per-day-of-week guard pushes the next attempt out a full week. The weekly re-nag would silently become fortnightly. Six days clears before every weekly tick.
- **Timestamp handling fails open.** An absent, unparseable or future-dated `offered_at` re-offers rather than staying silent, because silence is the failure mode the gate exists to stop. The empty-string case is guarded explicitly: GNU `date -u -d "" +%s` returns midnight today with exit 0, so a state file missing `offered_at` would otherwise have resolved to "offered today" and muted. Caught by the new suite running under GNU date in the chassis container after passing under BSD date on the host.
- New behavioural suite `chassis/scripts/test-chassis-update-check.sh` (wired into `shell-tests.yml`, no docker and no network - upstream is served from a temp dir over `file://` through the existing `CHASSIS_UPDATE_RAW_BASE` override) covers all five gates in 23 cases, including cooldown boundaries at the default window, the env-var override in both directions, dismissal outranking an expired cooldown, and every fail-open path. Seven of its cases fail against the pre-fix script, so the suite is proven to catch the defect rather than merely to pass.
- **`bake-env.sh` refuses a bake that collapses the key count.** It derives its key set by diffing the environment before and after sourcing `.env`, so any variable already present in the calling shell is subtracted out. Run it from a shell that has already sourced `.env` - easy to do by accident, since `bw-unlock.sh` and several gather scripts do exactly that - and it quietly wrote an almost-empty file while reporting success.
- **The dispatcher locks the state-file read-modify-write cycle, not just the temp path.** `set_state` and `increment_fire_count` shared one `${STATE_FILE}.tmp` staging path with no locking. A unique temp path per writer, which was the originally scoped fix, does not actually close the race.
- **`validate-heartbeats` strips env-prefixed gather args before resolving the path.** `gather_path="${value%% *}"` stripped trailing inline args but not a leading `KEY=VALUE` prefix, which is the documented way to parameterise a shared chassis gather per heartbeat. Such a heartbeat resolved its gather path to the env token and was permanently flagged as missing.
- **`daily-log-gather` day filters are exclusive on the upper bound.** `since_str <= x <= until_str` made every PR or issue event from "today" count as yesterday's work too, since the report's date field is `since_str`. A PR merged at 00:30 UTC landed in both days' logs.
- **`merge-plugin-triggers.sh` resolves plugins via `CHASSIS_PLUGINS_ROOT`.** It read manifests from `$CHASSIS_HOME/plugins/<name>` only, never the baked-plus-fetched overlay every other plugin-tree consumer uses (#95). In-container that path resolves to the customer-side `plugins/` dir, so a plugin fetched or baked into the chassis tree installed and validated cleanly but never got its Discord trigger registered, silently.
- **`diff-against-canonical` runs on every PR.** It is a required status check, and a path-filtered workflow never reports on a PR outside its paths, so branch protection blocked such PRs indefinitely on "Expected - Waiting for status to be reported". No red X, no log, nothing for a contributor to click.
- **`shell-lint` excludes the second zsh file (#144).** `test_state_write_race.sh` carries a `#!/bin/zsh` shebang and shellcheck has no zsh support, so it failed SC1071 while `ignore_names` listed only `heartbeat-dispatcher.sh`. "Shell scripts lint" had been red on `main` since 2026-08-02.

## v0.3.0 - 2026-07-21

The release that makes v0.2.0 real. ### Second brain

- **Notion accepts documents longer than 100 blocks.** `create_doc` and `append_to_doc` chunk into batches of at most 100 and issue a create followed by sequential appends. Previously any document over roughly 100 non-empty lines returned `HTTP 400: body.children.length should be <= 100`, which meant a full-length briefing could not be written at all.
- **Long paragraphs are no longer silently truncated.** Notion caps a single `rich_text` field at 2000 characters. The old code cut the content and reported success; it now splits across parts. This was losing text with no error.
- **Notion rate limiting is handled.** `_request` honours `Retry-After` (seconds or HTTP-date) with a bounded retry count. Only 429s are retried - Notion's limiter rejects before executing, so a retry cannot double-write. 5xx and network errors are deliberately not retried, because the write may have landed.
- **Chunked writes report partial failure precisely.** A failed chunk raises with the page id plus how many chunks of how many landed, so a retry is not blind. Partial content is left in place; a rollback delete can itself fail, and an append cannot distinguish its own blocks from pre-existing ones.
